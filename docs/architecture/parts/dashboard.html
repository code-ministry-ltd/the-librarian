Architecture overview

The dashboard is the only admin surface and reaches the server over the private listener

It is a Next.js app, and its browser code never talks to the server directly. Proposals are accepted or rejected here, never by an agent.

Writes follow the same path, using Server Actions in place of the proxy. The dashboard imports the server's AppRouter type at compile time, so an incompatible API change fails its build.

Source: apps/dashboard/app/api/trpc/[trpc]/route.ts, apps/dashboard/lib/trpc-server-bare.ts, ADR 0002.

Why is the dashboard a separate service?
Decision
Keep the admin UI in its own Next.js process.
Constraint
UI work must not risk agent availability, and the agent server's job is to answer JSON-RPC.
Rejected
One Next.js app that also serves /mcp; a richer UI inside the Node server; keeping the REST API and adding auth.
Cost accepted
Two builds to keep in sync and an extra hop for browser reads.
Source
ADR 0001 (observed)
Why is there still a one-container install?
Decision
An all-in-one image runs both processes under a small supervisor; the two-container Compose stack remains.
Constraint
Reason not recorded in an ADR. The self-host guide presents the single container as the low-friction path.
Rejected
Not recorded.
Cost accepted
The internal listener is loopback rather than a private Docker network.
Source
docker/all-in-one.Dockerfile, docker/supervisor.mjs (observed); reason inferred

Known limits

Owner sign-in is optional, controlled by LIBRARIAN_AUTH_ENABLED. Without it, anyone who can reach the dashboard port has admin access, so the published port defaults to 127.0.0.1 (docker/docker-compose.yml:107).
