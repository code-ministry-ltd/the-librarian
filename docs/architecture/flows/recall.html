Architecture overview

Recall ranks memories by section, then follows their links

A query searches only active memories. It combines keyword and meaning-based search, so an exact name and a loose description can both find the same note.

The steps

  1. Each memory is matched section by section, using keyword, vector, title and phrase signals fused by Reciprocal Rank Fusion (packages/core/src/store/corpus-index.ts:7, packages/core/src/store/index/hybrid-index.ts).
  2. Wikilink neighbours of direct matches are added in both directions, with a decayed score (packages/core/src/store/index/recall.ts).
  3. Results are over-fetched by four times the limit, with a floor of 24, so that filtering can still fill the limit. The default limit is 8 (corpus-index.ts:356-357).
  4. A memory with an open flag moves down the ranking but is never removed.
  5. With several shelves, each shelf's results are merged into one labelled list.
Why Reciprocal Rank Fusion?
Decision
Combine the signals by rank position.
Constraint
Keyword scores and cosine similarity are on incomparable scales.
Rejected
Changing the fusion method (a lower k or a weighted sum): deferred in favour of BM25 and an exact-phrase list, to be revisited only if those weren't enough.
Cost accepted
Only the order counts, so a much better match can't pull far ahead. k is 60.
Source
hybrid-index.ts comment (observed); hybrid ranking spec of 2026-06-19 and the memsearch field report, in the maintainer's private notes
Why embed locally?
Decision
EmbeddingGemma-300M runs in the server through node-llama-cpp, downloaded on first use (about 333 MB). A hash embedder is the fallback.
Constraint
The rearchitecture wanted local embeddings by default, with no setup and no GPU. Why this model replaced the originally planned bge models is not recorded. That it keeps memory text on the server is inferred.
Rejected
An API embedder was planned as a fallback; the code has no remote embedder today.
Cost accepted
CPU use on the host, capped at half its cores and no more than 6 threads by default.
Source
packages/core/src/store/index/resolve-embedder.ts (observed); spec 035 and the first-principles brainstorm, in the maintainer's private notes
Why are references searched separately?
Decision
Recall covers memories only. search_references builds its own references-only index for each call.
Constraint
Large research documents should be reusable without cross-talk into consolidated knowledge. The test was that adding a 23 KB document does not change memory recall.
Rejected
Consolidating references into memories, or injecting them at session start.
Cost accepted
An agent has to know which tool to ask.
Source
packages/core/src/store/corpus-index.ts:1-11 (observed); spec 035 F4 and the first-principles candidate shape, in the maintainer's private notes

Known limits

The candidate pool is bounded, so a very selective tag filter can return fewer results than the limit even when more matches exist (noted in corpus-index.ts:347-350). The in-memory index is built from the vault, so a large vault costs start-up work and memory.
