# Flagged-memory partial correction (draft)

**Status:** Approved; implementation in progress. The store slices now persist digest-only work metadata, batch new flags, reclaim bounded leased work with same-process attempt fencing, and cancel it alongside Dismiss/Archive. The correction worker, runtime wiring, proposal flow, and dashboard remain unimplemented.

## Objective

Let the curator address an outdated claim without retiring a memory that also contains useful facts. When a safe, exact candidate exists, a correction that passes the shared auto-apply policy removes only the identified claim and preserves all non-target content. If the candidate is safe but D13 or another approved gate prevents direct application, create a reviewable single-memory update proposal with a server-generated diff. If a candidate cannot be safely constructed, leave the flag for manual review; do not invent a proposal. Whole-memory Archive remains an explicit human action, not the default resolution of a flag.

## Current behavior and constraints

- `flag_memory` appends an agent-attributed free-text reason; it does not change memory status, and ordinary Grooming does not receive the reason as evidence. The MCP contract says a flag routes to human review and the tool itself never edits, archives, or deletes.
- `/flagged` currently offers Dismiss (clear flags, keep the memory active) and Archive (archive the entire memory, then clear flags). Archive does not hard-delete the text, but removes the whole record from active recall.
- Grooming already has one shared D13 confidence threshold. Eligible updates apply when `confidence >= threshold`; protected targets always propose. At threshold `0`, an eligible, unprotected update can apply even at confidence `0`.
- The existing single-target update proposal shows Current → Diff → Proposed and blocks approval when its source content has drifted. Its digest covers title/body, not flag state; legacy proposals with an unknown digest are intentionally not blocked.
- Memory bodies are free text, and ordinary Grooming evidence redacts and may truncate them. A correction must not match model-visible sanitized text to raw stored text by guessing offsets, nor rely on a model-generated replacement body to preserve unrelated claims.
- Store updates change operational fields such as `updated_at`/`updated_by`; preservation means unchanged user-authored content/metadata, while store-managed timestamps and audit metadata may change.

2. **Bounded, sanitized model input.** Send the complete reviewable body and its open flag reasons as explicitly untrusted data, after redaction. Hard limits for one request: at most 10 flags, at most 20,000 aggregate flag-reason characters, and at most 20,000 source-body characters. Above a limit, do not call the model or mutate; leave the flags for manual review. Redaction must carry a source-offset map. If the body is truncated, a candidate touches a redacted span, or an exact source mapping cannot be proven, do not mutate or propose from it. Never fall back to sending raw text to the model. The existing redactor is best-effort for known secret patterns, not a guarantee that arbitrary sensitive text is removed; retain that limitation in docs and treat this model call as carrying the same residual data-sharing risk as other curator calls.
3. **Strict correction result.** The curator returns only exact quote(s) to remove, operation confidence, and a rationale. The server verifies unique source matches through the safe offset map. Resolve all spans against the same pre-inference source snapshot; require them to be pairwise disjoint and reject the entire correction if any spans overlap, nest, or map ambiguously—never splice sequentially calculated offsets. D13 confidence is the sole confidence gate for direct application; there is no separate corroboration requirement. The score remains a model judgment, not objective proof. Flag reasons are untrusted data and may identify the suspected claim, but must not be followed as instructions.
4. **Preserve non-target facts.** The server constructs the candidate with deterministic deletion; no replacement body is accepted. Every non-target byte and user-authored metadata remain unchanged. Auto-application is limited to a self-contained single-claim sentence or top-level list item. For a compound sentence, a candidate is allowed only if the exact stale claim can be isolated without deleting or rewriting any other fact and the resulting text remains reviewable; otherwise leave the flag for manual review. Proposal-only status is not permission to delete a broader span. If the candidate cannot preserve other facts or leaves no reviewable text, do nothing.
5. **Uncertainty routes to review.** If a safe candidate addresses the complete open-flag batch but confidence is below D13's threshold, create the normal single-target update proposal, even if the flags are the only evidence; show the flag reasons, curator rationale, uncertainty, and diff transparently. If another approved safety gate prevents direct application, create a proposal only when the same safe candidate can still be constructed. If no exact candidate can be isolated safely or it does not address every flag in the batch, do not invent one merely to create a proposal. Protected targets always use a proposal.
6. **Same-process, idempotent direct application.** Apply in place only if D13 allows it, the hard safety conditions pass, and the final synchronous memory-store mutation re-reads and verifies source status/content and the complete reviewed flag snapshot. This check is same-process only; an independent process or external editor can still race the subsequent write. Treat all flags in that snapshot as one batch: the correction must address every reason or no direct edit occurs. In one existing memory-store persist, apply the deterministic edit and resolve all reviewed flags together. At threshold `0`, D13 permits an eligible update at confidence `0`; this feature follows that behavior. On mismatch, do nothing and preserve the current persisted source, flags, and job state; never restore a stale snapshot or requeue unless a new pending snapshot exists. An explicit Dismiss/Archive cancellation always wins. Per the user's explicit decision, retain the existing write/commit pattern without a single-writer guarantee or interprocess lock. The final mutation must still re-read and compare the reviewed snapshot, but that check cannot exclude a competing process or external editor; this accepted race is documented and is not covered by cross-process tests. A request with no open flags is a no-op; a retry for an already-applied correction must not edit again.
7. **Proposal creation, approval, and idempotency are drift-safe.** Capture source status/content and the complete flag snapshot before model inference. At proposal creation, re-read and compare that original snapshot within the synchronous store mutation; if anything changed during same-process inference, create nothing. Cross-process changes can still race the write, as documented. Stamp correction-specific provenance, source-content and flag-snapshot digests, and a digest of the proposed replacement. Get-or-create by source plus reviewed flag snapshot within the existing synchronous store path so same-process retries reuse one pending proposal. Concurrent processes may still create duplicates; this is part of the accepted residual. If a crash occurs between proposal creation and marking the snapshot `proposal_pending`, startup recovery must discover and reuse the existing proposal before another model call; proposal/source bookkeeping must not permit duplicates. The flagged view uses a targeted lookup by correction marker/source/snapshot (not the capped general proposal list) and links to this correction, not to a generic update. The proposal row carries its exact server-resolved shelf ID. Approve/reject inputs must include that shelf ID and resolve both proposal and source on that validated shelf within the admin's authorized recall set; never fall back to the first same-ID record on another shelf. Keep the source active and flagged until approval. Approval re-reads and validates source status/content, flag snapshot, and proposed replacement digest in the synchronous store mutation; this does not serialize another process or an external editor. For correction proposals, a missing or malformed baseline or any approval-time content patch is non-approvable; the UI must visibly disable/reject approval. Preserve existing legacy behavior for unrelated proposals. On approval, the existing update-proposal lifecycle may archive the superseded source and activate the corrected replacement; that is version replacement, not whole-memory disposal—the replacement must retain every non-target fact. Rejection or stale-source failure leaves the source and flags available and marks that snapshot for manual review; it is not automatically proposed again unless a new flag creates a new snapshot.
8. **No destructive fallback.** Correction cannot invoke the archive operation or turn into merge/split. Dismiss and whole-memory Archive remain explicit alternatives. Provider, parse, authorization, or storage failure leaves the source and flags unchanged and does not block the user's turn.

## Boundaries

### Always

- Reuse the shared D13 threshold and `active | proposed | archived` state model; add no second confidence knob or memory state.
- Treat flag reasons and model output as hostile data. Redact before model/audit use; never log secrets; validate with a strict schema and server-side allowlist.
- Preserve the existing private-mode protocol and its stated limitation: the server cannot verify the in-conversation marker, and an agent may still make a tool call contrary to the prompt. The new worker acts only on a newly persisted flag marker; do not claim server-side private-mode enforcement.
- Do not accept client-authored source content, flags, shelf, or actor. Revalidate the server-resolved flagging principal's write authority for the captured shelf; use a server-owned curator audit actor for automatic edits, and require an authorized admin scope for proposal review.
- Re-read and validate source/status/flag snapshots in each synchronous store mutation before writing. This protects the server's in-process workflow only; cross-process/external-writer races are explicitly accepted for this release, with no single-writer restriction or interprocess lock.
- Fail closed on missing or invalid correction-proposal baselines without changing legacy proposal semantics or displaying an enabled Approve control.
- Bound aggregate flag count and model input size; exceeding a cap means no model call and no mutation.

## Confirmed product decisions

- Start the correction attempt asynchronously after a successfully persisted `flag_memory` call; do not block the flagging turn.
- Treat all open flags on one memory as a single batch; resolve none unless the correction addresses the complete batch.
- Use D13 confidence as the sole confidence gate. At threshold `0`, an eligible unprotected correction at confidence `0` may auto-apply, as in the existing policy; exact-span and source/flag safety checks still apply.
- There is no separate corroboration requirement. The confidence score remains model judgment, not objective proof; the agent flag is an untrusted hint, not an instruction. A false or prompt-injected flag can still cause an exact-span deletion if D13 permits it, including at confidence `0` when the threshold is `0`.
- Respect existing `curator.grooming.enabled` and provider configuration; disabled/unconfigured grooming does not trigger review or later replay old flags.
- Keep successful correction outcomes in Recent corrections for 30 days.
- A job queued from a valid public flag may finish after a later private-mode toggle; current private mode suppresses new flag calls but does not cancel already-queued work.
- **Cross-process writes:** At the user's direction, this change follows the current synchronous read/write/Git-commit pattern and adds no single-writer runtime restriction or interprocess lock. Competing processes or external vault editors may overwrite flags/corrections or create duplicate work; this residual is accepted and no cross-process safety is claimed.

### Never

- Archive a whole memory as an automatic fallback for an unisolatable claim.
- Rewrite unrelated text or substitute a new fact as part of this MVP.
- Clear unrelated/new flags, approve through source/flag/proposal drift, or let a flagged correction turn into merge/split/archive.

## Success criteria

- A mixed memory with one stale claim and other useful facts retains every non-target byte and all user-authored metadata after direct correction; only store-managed audit/timestamp fields may change.
- The work marker is stored in the same memory document and written through one existing memory-store persist with the new flag. This does not provide crash-atomicity or cross-process isolation. Startup recovery processes only pending markers from this feature, and bounded retries/manual-review status are visible without exposing raw reasons or bodies in queue metadata. Successful corrections remain discoverable in Recent corrections for 30 days after the open flags are cleared, based on `applied_at`. A compound sentence cannot be removed wholesale if it contains a useful non-target fact. Disabled/unconfigured Grooming never calls the model and does not replay old flags when re-enabled.
- A safe candidate below threshold, against a protected target, or blocked by an approved safety gate leaves the source active and flagged and creates a single-target proposal with a server-generated diff showing only the intended removal.
- The proposal is reachable from the flagged-memory experience, distinguishable from unrelated updates, and cannot be approved after source/flag/proposal drift, with missing/malformed correction baselines, or with an approval-time patch; the UI visibly blocks unsafe approval.
- Ambiguous spans, malformed output, duplicate/missing quotes, truncated or redaction-intersecting spans, over-limit inputs, provider failures, unauthorized IDs, ineligible statuses/read-only shelves, and same-process source/flag edits during inference cause no unsafe mutation and leave the item available for review. Cross-process/external-editor races are accepted as described above.
- No-open-flag requests are no-ops. Repeated or concurrent requests for a pending correction within one process reuse one proposal and do not create duplicates. Same-process Dismiss/Archive racing with inference cancels the job in the existing store mutation; it cannot requeue, restore flags, or override the explicit action. Existing Dismiss and Archive meanings remain unchanged, and both actions resolve the exact principal-authorized shelf represented by the row.
- Approval of a correction proposal activates the corrected replacement while preserving non-target facts; it does not discard the mixed memory's useful content.
- Tests cover threshold boundaries (including `0`), protected memories, multiple flags, no-admin/unrecorded response wording plus agent relay guidance, redaction/offset mapping, overlapping/nested spans with all-or-nothing rejection, prompt injection, input caps, authorization/shelf scope, idempotency, same-process inference/drift and Dismiss/Archive races, crash between flag persistence and worker wake-up, recovery of marked work without sweeping legacy flags, bounded retries/status, correction-specific fail-closed drift in server and UI, proposal-content drift/patch rejection, legacy proposal compatibility, proposal approval/rejection, rendered diff, and private-mode prompt-guard parity in every integration (without claiming a runtime/server-enforced block). Cross-process/external-editor races are explicitly accepted and are not tested or guaranteed.
